# Detecção local experimental

Somente para testes locais autorizados: o servidor escuta em 127.0.0.1. Não publicar nem usar dados reais. São necessários PostgreSQL isolado, servidor SMTP de teste em 127.0.0.1 e Node. Execute as migrações em ordem: infra/001_initial.sql, infra/002_alerts.sql e infra/003_projects.sql e infra/004_observation_sources.sql. Cadastre um projeto na API administrativa local autenticada (POST /admin/projects com JSON `name` e `origin`) e configure DATABASE_URL, PROJECT_ID com o ID retornado, SMTP_PORT e opcionalmente PORT; execute npm ci, npm run build e npm start. GET /admin/projects lista cadastros; GET /admin/projects/{id}/observations e /incidents consultam registros do projeto. Essas rotas exigem Bearer da sessão administrativa e não aceitam requisições com Origin. Cada processo de detecção usa um único projeto configurado pelo operador, não um ID enviado pelo navegador. A origem é carregada ao iniciar; reinicie o processo após eventual alteração no banco. Para importar um projeto legado, aplique as migrações e inicie uma vez com o PROJECT_ID e ALLOWED_ORIGIN anteriores: o servidor cria o cadastro com o mesmo ID, preservando os registros. Uma origem já atribuída a outro ID ou uma origem divergente para um ID existente impede a inicialização. Remova ALLOWED_ORIGIN após conferir o cadastro. Registros órfãos não são associados automaticamente. As páginas controladas de tests/fixtures usam a porta 3000. Para executar a suíte, configure TEST_DATABASE_URL para banco isolado, instale Chromium com npx playwright install chromium e execute npm test. No CI, PostgreSQL, SMTP de teste e Chromium são reais e isolados.

O navegador envia apenas sua origem alegada, que é forjável mesmo quando coincide com Origin; ela não comprova uma cópia. Incidentes permanecem unverified. Não se executam URLs informadas nem se coletam caminhos, query, IP ou identidade do visitante. Observações são deduplicadas por projeto, host e dia UTC; expiram após 7 dias. Incidentes inativos e suas intenções de alerta expiram após 30 dias. A limpeza ocorre ao iniciar e periodicamente enquanto o processo está ativo. Há limite de 60 requisições por minuto por processo e 100 incidentes por projeto durante a retenção; esses limites podem descartar sinais legítimos e não substituem controles públicos. Reiniciar o processo reinicia o limite de taxa, mas não o teto persistente.

A transação grava incidente e intenção de alerta juntos. Uma intenção por incidente é enviada ao SMTP local e marcada como enviada; falhas são tentadas novamente após um minuto. Um lock do PostgreSQL impede envios simultâneos pelo mesmo projeto. Se o SMTP aceitar a mensagem e o processo falhar antes de registrar sent_at, a próxima tentativa pode duplicá-la: SMTP não garante entrega exatamente uma vez. O endereço de remetente e destinatário é fixo e reservado a testes. Antes de qualquer publicação são necessários autenticação administrativa, configuração segura de SMTP, controles de abuso adequados, revisão de privacidade e testes operacionais adicionais.

A instalação de laboratório usa `<script src="http://127.0.0.1:3000/runtime.js"></script>`: esse bootstrap carrega `/core.js` do mesmo servidor, e o Core envia a origem alegada ao endpoint existente. A configuração do projeto e a comparação pertencem ao servidor, que lê a origem no PostgreSQL ao iniciar; nenhum ID público autentica o navegador. Bootstrap ou Core bloqueado, ou backend indisponível, deixa a página utilizável, mas nenhuma observação é garantida. Não há fallback independente, canários, redirecionamento, alteração de CTA ou modo invisível. Não há classificação de instalação FULL/PARTIAL/UNSUPPORTED comprovada; CSP, outros navegadores e ambientes de produção não foram validados nesta fatia.
