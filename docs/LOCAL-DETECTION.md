# Detecção local experimental

Somente para testes locais autorizados: o servidor escuta em 127.0.0.1. Não publicar nem usar dados reais. São necessários PostgreSQL isolado, servidor SMTP de teste em 127.0.0.1 e Node. Execute as migrações em ordem: infra/001_initial.sql, infra/002_alerts.sql e infra/003_projects.sql, infra/004_observation_sources.sql, infra/005_canaries.sql, infra/006_page_redirect.sql, infra/007_protection_policy.sql, infra/008_traffic_observations.sql e infra/009_risk_assessments.sql. Cadastre um projeto na API administrativa local autenticada (POST /admin/projects com JSON `name` e `origin`) e configure DATABASE_URL, PROJECT_ID com o ID retornado, SMTP_PORT e opcionalmente PORT; execute npm ci, npm run build e npm start. GET /admin/projects lista cadastros; GET /admin/projects/{id}/observations e /incidents consultam registros do projeto. Essas rotas exigem Bearer da sessão administrativa e não aceitam requisições com Origin. Cada processo de detecção usa um único projeto configurado pelo operador, não um ID enviado pelo navegador. A origem é carregada ao iniciar; reinicie o processo após eventual alteração no banco. Para importar um projeto legado, aplique as migrações e inicie uma vez com o PROJECT_ID e ALLOWED_ORIGIN anteriores: o servidor cria o cadastro com o mesmo ID, preservando os registros. Uma origem já atribuída a outro ID ou uma origem divergente para um ID existente impede a inicialização. Remova ALLOWED_ORIGIN após conferir o cadastro. Registros órfãos não são associados automaticamente. As páginas controladas de tests/fixtures usam a porta 3000. Para executar a suíte, configure TEST_DATABASE_URL para banco isolado, instale Chromium com npx playwright install chromium e execute npm test. No CI, PostgreSQL, SMTP de teste e Chromium são reais e isolados.

O Core envia origem alegada e, quando presentes, click-ID limitado, utm_medium permitido e hostname do referrer. Esses sinais transitam temporariamente e podem ser forjados. O servidor persiste somente classe, tipo de evidência, fonte permitida e incerteza; não armazena valores brutos, URLs completas, caminhos, query, IP ou identidade. Incidentes permanecem unverified. Observações são deduplicadas por projeto, host, fonte e dia UTC; incidentes inativos e alertas expiram após 30 dias. A limpeza ocorre periodicamente. O limite de 60 requisições por minuto e 100 incidentes por projeto pode descartar sinais legítimos e não substitui controles públicos.

A transação grava incidente e intenção de alerta juntos. Uma intenção por incidente é enviada ao SMTP local e marcada como enviada; falhas são tentadas novamente após um minuto. Um lock do PostgreSQL impede envios simultâneos pelo mesmo projeto. Se o SMTP aceitar a mensagem e o processo falhar antes de registrar sent_at, a próxima tentativa pode duplicá-la: SMTP não garante entrega exatamente uma vez. O endereço de remetente e destinatário é fixo e reservado a testes. Antes de qualquer publicação são necessários autenticação administrativa, configuração segura de SMTP, controles de abuso adequados, revisão de privacidade e testes operacionais adicionais.

A instalação de laboratório usa `<script src="http://127.0.0.1:3000/runtime.js"></script>`: esse bootstrap carrega `/core.js` do mesmo servidor, e o Core envia a origem alegada ao endpoint existente. A configuração do projeto e a comparação pertencem ao servidor, que lê a origem no PostgreSQL ao iniciar; nenhum ID público autentica o navegador. Instale tambem `<script src="http://127.0.0.1:3000/fallback.js"></script>` diretamente na pagina, separado do bootstrap. O fallback envia somente a origem alegada. Os rotulos core e fallback sao alegacoes forjaveis, nao autenticam o sinal nem provam copia ou identidade. As duas fontes compartilham servidor, banco, rede e limite de taxa; falhas comuns ou bloqueio de todos os mecanismos impedem observacao. Incidente e alerta sao compartilhados por projeto e host. Registros legados browser_claim conservam fonte desconhecida. Redirecionamento existe apenas no ensaio controlado de LOW; troca de CTA nao existe. Nao ha classificacao FULL/PARTIAL/UNSUPPORTED comprovada; CSP e outros navegadores nao foram validados.


Canarios passivos de laboratorio sao instalados diretamente no HTML e no CSS, independentes de JavaScript: `<img alt="" width="1" height="1" src="http://127.0.0.1:3000/canary/html.gif">` e uma regra CSS aplicada a elemento renderizado, por exemplo `background-image: url(http://127.0.0.1:3000/canary/css.gif)`. Nao altere estilos ou navegacao existentes para instala-los. Consulte `canary_observations` no PostgreSQL local filtrando por project_id: source distingue html_canary e css_canary; host vazio significa desconhecido. Host provem exclusivamente de Referer nao autenticado, nao e prova de copia ou identidade; nao cria incidente ou alerta. Sao armazenados projeto, fonte, host, dia e horario da observacao; deduplicacao por projeto/host/fonte/dia, limite de 1400 registros por projeto e retencao de 7 dias. Ambos compartilham o limite por processo. A ausencia de Referer ou sinais nao prova fraude nem adulteracao. CSP, cache, bloqueadores, politica de navegador e rede podem impedir requisicoes; todos compartilham servidor e rede. O endpoint e restrito a loopback e nao deve ser publicado.

A atribuição representa presença deduplicada por projeto, host, dia UTC, classe e fonte, não contagem de visitas ou sessões. Os sinais declarados não são corroborados; a classe não altera risco nem habilita redirect. DIRECT_UNKNOWN não significa acesso direto comprovado. Registros expiram 7 dias após a primeira observação e a limpeza é periódica. Busca reconhecida limita-se a google.com, bing.com e duckduckgo.com e não comprova busca real.

The lab-risk-v1 assessment returns UNCERTAIN for insufficient evidence. LOW is only a controlled local fixture, not an operational classification. HIGH is reserved by the contract and is not produced by this evaluator. Evaluation or persistence failure yields OBSERVE_ONLY. Minimal records by project, host and day expire after seven days; source, reason and confidence describe the assessment, not identity. The project limit is 1400 records; capacity exhaustion suppresses visible action.
